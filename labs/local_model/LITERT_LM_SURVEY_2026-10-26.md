# LiteRT-LM survey (2026-10-26)

Question: could Zynkbot's on-phone model (Qwen3-4B-Instruct-2507, today a Q4_0 GGUF on the CPU through llama.cpp, roughly 3-6 words/s on a Pixel 10 Pro XL) run instead through Google's LiteRT-LM engine on the Pixel's GPU or its Tensor TPU? This note states what is published as of 2026-10-26. It makes no recommendation.

Terms: LiteRT is Google's on-device machine-learning runtime (the successor to TensorFlow Lite). LiteRT-LM is the large-language-model engine built on it. ".litertlm" is LiteRT-LM's model file format. "Prefill" is reading the prompt; "decode" is writing the answer, measured in tokens per second (a token is roughly three quarters of a word). "AOT" means ahead-of-time: compiling the model for a specific chip on a PC before shipping it. "JIT" means compiling on the phone at run time. "NPU/TPU" is the chip's dedicated AI accelerator; on Pixels it is the Tensor TPU.

## 1. Current release, file format, Android API

The latest LiteRT-LM release is v0.18.1, tagged 20 October; the GitHub page omits the year, but the Google Maven index for the Android library shows 0.18.1 published 2026-10-20 (https://github.com/google-ai-edge/LiteRT-LM/releases, fetched 2026-10-26; https://dl.google.com/android/maven2/com/google/ai/edge/litertlm/litertlm-android/maven-metadata.xml, lastUpdated 20261020). v0.18.0 (6 Oct) added EmbeddingGemma 2; v0.18.1 only fixes a source-build ABI problem (same releases page). The engine loads ".litertlm" files; the older ".task" files belong to the MediaPipe route, which the Gemma 4 model cards describe as "currently in maintenance mode" (https://github.com/google-ai-edge/LiteRT-LM README, fetched 2026-10-26; https://huggingface.co/litert-community/gemma-4-E4B-it-litert-lm, fetched 2026-10-26). There is a Kotlin API for third-party apps: Gradle coordinate com.google.ai.edge.litertlm:litertlm-android, classes Engine/EngineConfig/Conversation, backend chosen explicitly with Backend.CPU(), Backend.GPU() or Backend.NPU(nativeLibraryDir), and for GPU the app must add uses-native-library entries for libOpenCL.so and libvndksupport.so to its manifest (https://developers.google.com/edge/litert-lm/android, last updated 2026-09-04). The 0.18.1 AAR declares minSdkVersion 24 (read from the AAR's AndroidManifest.xml, downloaded 2026-10-26).

## 2. Official ready-made .litertlm files (Google or litert-community)

The Hugging Face "litertlm" tag lists 185 repos, most under litert-community (https://huggingface.co/models?other=litertlm, fetched 2026-10-26). For the families asked about:

- Gemma 3 1B (litert-community/Gemma3-1B-IT): gemma3-1b-it-int4.litertlm, 1B, dynamic int4 QAT, 529 MB, context 2048, CPU and GPU; plus Gemma3-1B-IT_q4_ekv1280_sm8750.litertlm (a16w4, context 1280) for the Qualcomm NPU. S24 Ultra: CPU 379/55 tok/s, GPU 2531/49 tok/s (prefill/decode); S25 Ultra NPU 5836/85 (https://huggingface.co/litert-community/Gemma3-1B-IT, fetched 2026-10-26). Google's LiteRT-LM NPU guide also lists Gemma3-1B 8-bit for Tensor_G5 and Tensor_G6 at context 1280 (https://developers.google.com/edge/litert/next/litert_lm_npu, last updated 2026-09-02).
- Gemma 3n E2B / E4B (google/gemma-3n-E2B-it-litert-lm, google/gemma-3n-E4B-it-litert-lm, both gated behind the Gemma licence): one file each, gemma-3n-E2B-it-int4.litertlm / gemma-3n-E4B-it-int4.litertlm, int4 weights, file sizes not shown on the cards, 32K context. E2B card shows CPU, GPU and a MediaTek NPU row (S24 Ultra GPU 816/15.6); E4B card shows CPU and GPU only (S24 Ultra GPU 548/9.4) (https://huggingface.co/google/gemma-3n-E2B-it-litert-lm and https://huggingface.co/google/gemma-3n-E4B-it-litert-lm, fetched 2026-10-26).
- Gemma 3 4B (litert-community/Gemma3-4B-IT): only web ".task" files (int8 3.9 GB, int4 2.56 GB, Q4_0 2.89 GB), benchmarked on a MacBook GPU in Chrome; no .litertlm file and no Android row (https://huggingface.co/litert-community/Gemma3-4B-IT, fetched 2026-10-26).
- Gemma 4 E2B / E4B (litert-community/gemma-4-E2B-it-litert-lm, -E4B-): E2B main file 2583 MB, mixed 2/4/8-bit, context up to 32K, CPU and GPU, plus a Qualcomm QCS8275 NPU file; E4B main file 3654 MB, CPU and GPU, no NPU file. - Qwen3 (litert-community): 0.6B (four files: int8 586 MB ctx 4096; MediaTek NPU a16w8 992 MB; mixed int4 475 MiB ctx 2048; int4 block-32 329 MB ctx 4096; CPU, GPU, MediaTek NPU), 1.7B (int8 2.1 GB; int4 block-32 932 MB ctx 4096; CPU and GPU), 4B (int8 5.28 GB ctx 4096; mixed int4 2535.88 MiB ctx 2048; card shows GPU only), 4B-Instruct-2507 (qwen3_4b_instruct_2507_mixed_int4.litertlm, 2535.88 MiB, ctx 2048, GPU: WebGPU on desktop and OpenCL on Android; CPU appears only as a comparison row), 4B-Thinking-2507, 8B (int8 7.74 GB; int4 4.66 GB), 14B, and Qwen3.5 0.8B/2B/4B (https://huggingface.co/litert-community/Qwen3-0.6B, https://huggingface.co/litert-community/Qwen3-1.7B, https://huggingface.co/litert-community/Qwen3-4B, https://huggingface.co/litert-community/Qwen3-4B-Instruct-2507, all fetched 2026-10-26; the tag listing for the rest).

Note on backends: no litert-community card fetched here lists a Google Tensor NPU row; the only phone NPU rows are Qualcomm (S25 Ultra) and MediaTek (vivo).

## 3. Converting Qwen3-4B yourself

The converter repo google-ai-edge/ai-edge-torch now redirects to google-ai-edge/litert-torch (GitHub API returned "Moved Permanently" for the old name, 2026-10-26). The Qwen3 example lives at litert_torch/generative/examples/qwen/qwen3.py with build_0_6b_model, build_1_7b_model and build_4b_model; convert_v3_to_tflite.py takes --model_size in {0.6b, 1.7b, 4b}; verify_qwen3.py maps those to the Hugging Face checkpoints Qwen/Qwen3-0.6B, Qwen/Qwen3-1.7B and Qwen/Qwen3-4B (https://github.com/google-ai-edge/litert-torch/tree/main/litert_torch/generative/examples/qwen, files read 2026-10-26). The newer documented route is `litert-torch export_hf --model=<HF id or local dir>`, which supports the Qwen3ForCausalLM architecture, downloads from the Hugging Face hub or loads a local safetensors directory, and writes a .litertlm; GGUF is not mentioned anywhere on the page (https://developers.google.com/edge/litert/conversion/pytorch/genai, last updated 2026-09-02). The default recipe is per-channel int8 weights (dynamic_wi8_afp32); the page names no int4 recipe, though the published Qwen3-1.7B file is labelled dynamic_wi4b32_afp32, so an int4 recipe exists in the quantizer (https://huggingface.co/litert-community/Qwen3-1.7B, fetched 2026-10-26). Separately, the published Qwen3-4B-Instruct-2507 file was made "from the original Hugging Face checkpoint" with a TorchAO mixed-int4 recipe, so conversion of this exact model has been done by Google's community org (https://huggingface.co/litert-community/Qwen3-4B-Instruct-2507, fetched 2026-10-26).

## 4. Tensor NPU for third-party apps

Google's NPU page lists Google Tensor as a supported vendor "through the CompiledModel API" (AOT only) and carries the line "Beta: Google Tensor SDK doesn't yet support on-device (JIT) compilation"; the runtime ships as the Maven package com.google.ai.edge.litert:litert-npu-runtime-google-tensor from release 2.3.0, minSdk 31, arm64 only (https://developers.google.com/edge/litert/next/npu, last updated 2026-10-12). The compiler itself is gated: the Tensor SDK page names targets Tensor_G5 and Tensor_G6 only and says "Sign up for access to Google Tensor SDK Beta" via a form whose URL contains "experimental_access" (https://developers.google.com/edge/litert/next/tensor-sdk, last updated 2026-09-08). Users report the compile stack as pip ai-edge-litert (2.1.6) plus ai-edge-litert-sdk-google-tensor, with an environment variable GOOGLE_TENSOR_SDK_BETA pointing at the tarball obtained through that sign-up (https://github.com/google-ai-edge/LiteRT/issues/8062, opened 2026-06-12, closed 2026-08-12). The export tool documents `--aot_backend=GOOGLE --aot_soc_model=Tensor_G6` for plain LiteRT models, but the .litertlm package compiler accepts only qualcomm and mediatek and raises "Unsupported backend: google_tensor" (https://developers.google.com/edge/litert/conversion/pytorch/genai, 2026-09-02; https://github.com/google-ai-edge/litert-torch/issues/1383, opened 2026-10-26, open, labelled feature). LiteRT issue 11251 (opened 2026-10-26, open, "awaiting LiteRTer") reports that on a Pixel 10 Pro the system EdgeTPU service refuses on-device compilation because the app "is not in the EdgeTPU allowed list", the model silently falls back to CPU, and a pre-compiled Tensor_G5 model from the same app does run on the TPU; no maintainer answer yet (https://github.com/google-ai-edge/LiteRT/issues/11251). For LLMs specifically, Google's LiteRT-LM NPU guide shows the Tensor path only as a Bazel source build of the engine plus the Google Tensor dispatch library, and lists just Gemma3-1B (G5/G6) and Gemma4-E2B (G6) (https://developers.google.com/edge/litert/next/litert_lm_npu, 2026-09-02). A Pixel 10 Pro XL AOT report (plain model, not an LLM) was closed by its reporter after matching toolchain versions and setting useLegacyPackaging=true so the dispatch .so is extracted (https://github.com/google-ai-edge/LiteRT/issues/7787, opened 2026-06-03, closed 2026-06-04).

## 5. Published speed numbers on Pixel GPUs

No Google source gives tokens/s for LiteRT-LM on a Pixel 9 or Pixel 10; the litert-community cards benchmark Samsung, vivo and TECNO phones (all cards above, fetched 2026-10-26). The nearest Pixel figures are community issues: Pixel 8, Gemma 4 E2B, LiteRT-LM 0.10.x: CPU 53.4/10.6 tok/s, GPU (patched) 426.6/11.9 tok/s prefill/decode (https://github.com/google-ai-edge/LiteRT-LM/issues/1850, opened 2026-04-03, closed 2026-09-30); Pixel 9, Gemma 4 E2B: "GPU about 2x faster than CPU", no absolute number (https://github.com/google-ai-edge/LiteRT-LM/issues/1915, opened 2026-04-09); Pixel 10 Pro Fold, Qwen3-0.6B: "~3.5 tok/s", backend and phase unstated (https://github.com/google-ai-edge/LiteRT-LM/issues/2566, opened 2026-06-13). For the Qwen3-4B-Instruct-2507 file itself the published Android numbers are Samsung SM-S937U1 (a Galaxy S25-series phone) GPU 375.7/18.5 at v0.13.1, and Galaxy S26 (Snapdragon 8 Elite Gen 5) GPU 306/19.9 versus CPU 46-56/8.4-9.2 at v0.16.0, with GPU engine init of 16-21 s per process (https://huggingface.co/litert-community/Qwen3-4B-Instruct-2507, fetched 2026-10-26). The AI Edge Gallery release coverage gives only relative gains (up to 2.2x decode with multi-token prediction) and no Pixel figure (https://aiweekly.co/alerts/google-ai-edge-gallery-adds-gemma-4-mtp-and-pixel-tpu, 2026-05-19).

## 6. Known limits

Context: each .litertlm carries a fixed context size (the Qwen3-4B-Instruct-2507 int4 file is 2048 tokens, the Qwen3-4B int8 file 4096, Gemma 4 up to 32K); the app sets max_num_tokens but there is no API to read a file's ceiling (https://github.com/google-ai-edge/LiteRT-LM/issues/2865), and on GPU the KV cache is allocated for the full max_num_tokens, about 76 KB per token on Gemma 4 E4B (https://github.com/google-ai-edge/LiteRT-LM/issues/4096). GrapheneOS: no official statement found; one report shows Gemma 4 E4B running on the OpenCL GPU backend of LiteRT-LM 0.18.0 on a Pixel 10 Pro under GrapheneOS, with black flickering lines on screen during GPU work that stop with Developer Options "Disable HW overlays" (https://github.com/Emphasize5599/gasket/issues/1, opened 2026-10-20); the linked GrapheneOS tracker entry about Pixel 10 corruption under GPU load is open and labelled "upstream", with no mention of LiteRT (https://github.com/GrapheneOS/os-issue-tracker/issues/6757, opened 2025-12-11). Older Pixels: Backend.GPU() on a Pixel 8 Pro fails at inference with "Can not find OpenCL library" (https://github.com/google-ai-edge/LiteRT-LM/issues/1860, opened 2026-04-05, open), while a maintainer says internal tests show Gemma 4 E2B working on Pixel 8 GPU (issue 1850, 2026-09-30). 16 KB pages: no official note found; a direct check of the published litertlm-android-0.18.1.aar shows both liblitertlm_jni.so builds (arm64-v8a, x86_64) with LOAD segment alignment 0x4000, i.e. 16 KB (readelf on the AAR downloaded from Google Maven, 2026-10-26); a third-party app's CI also reports liblitertlm_jni.so from 0.17.1 passing the p_align=0x4000 check (https://github.com/NickMonrad/kernel-ai-assistant/issues/1653, closed 2026-10-25).

## Bottom line

Can Qwen3-4B-Instruct-2507 be run through LiteRT-LM today: yes. Google's litert-community org already publishes qwen3_4b_instruct_2507_mixed_int4.litertlm (2.5 GB, 2048-token context), it loads through the public Kotlin library litertlm-android 0.18.1, and its own conversion path (litert-torch export_hf from the safetensors checkpoint, not from GGUF) also covers the Qwen3 architecture at 4B. Is the Pixel GPU path available to a third-party app today: yes in the sense that the library, the OpenCL backend and the manifest entries are public, and one report shows it working on a Pixel 10 Pro under GrapheneOS with a display-flicker side effect; but no published tokens/s exists for any Pixel 9 or 10, the published Snapdragon GPU decode for this file is 18-20 tok/s, and GPU engine start-up is reported at 16-21 s. Is the Tensor NPU path available today: no for this model. No Qwen .litertlm for Tensor is published, the .litertlm NPU compiler has no Google Tensor backend, the Tensor compiler SDK is a sign-up beta, on-device compilation is refused for apps not on Google's allowlist, and Google's own LiteRT-LM NPU instructions for Tensor require building the engine and dispatch library from source. Whether any of this changes a Pixel 10 Pro XL's 3-6 words/s is unknown from published sources.
